# ADR-001 — No NavController for Sprint 1–2

## Status

Accepted

## Context

The app initially has three screens: PermissionScreen, ScanScreen, PacketLogScreen.
Navigation between them is fully determined by app state (permission granted/denied,
connection state). There is no user-initiated navigation beyond tapping a device in the list.

## Decision

Use a simple `when` block in `RtrCompanionApp.kt` to route between screens based on
`ViewModel` state, with no `NavController` or `Navigation Compose` dependency.

## Alternatives Considered

- **Navigation Compose** — Adds complexity and a new dependency for what is essentially
  one linear path with no back stack requirements. Premature for Sprint 1.
- **Fragment-based navigation** — Not applicable; the project is fully Compose.

## Reasoning

The KISS principle applies. Three screens with deterministic state-based transitions
do not need a navigation graph. The router is easy to read and understand.

## Consequences

- **Positive:** Zero navigation boilerplate, no NavController lifecycle handling, no
  route string maintenance.
- **Negative:** When Sprint 4 adds a settings screen or multi-pane layouts, this will
  need to be replaced with Navigation Compose. The transition is straightforward.

## Review Trigger

Revisit when the app requires more than four screens or needs back-stack support.
