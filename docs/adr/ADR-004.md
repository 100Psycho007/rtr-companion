# ADR-004 — Authentication Handshake Implementation

## Status

Accepted (Pending hardware verification of AES key)

## Context

The RTR 310 does not stream live telemetry to unauthenticated BLE clients.
During Sprint 3 hardware testing, the app connected successfully and the CCCD
notification enable succeeded, but no live packets were received during normal
operation. Only a shutdown burst was captured when the bike powered off.

Cross-referencing with the JupiterRideCompanion project
(github.com/overclock98/JupiterRideCompanion), which uses the identical TVS
SmartXonnect BLE service UUID and characteristics, confirmed that the protocol
requires a cryptographic handshake before the bike streams telemetry:

1. Bike sends a challenge: `0x9A 0xF2` + 16 random bytes
2. Phone encrypts the 16 bytes using AES-128-CTR (zero IV, no padding)
3. Phone sends response: `0x9A 0xF1` + encrypted bytes to CHAR_WRITE

Additionally, a keep-alive ping packet (`0x5B 0x4A`) must be sent continuously
to maintain the connection and update the cluster display.

## Decision

1. Implement `HandshakeManager` in `ble-core/auth/` to detect challenge packets
   and build encrypted responses.
2. Implement `PingPacketBuilder` in `ble-core/ping/` to build keep-alive packets.
3. Wire both into `RtrGattManager` — challenge response sent immediately when
   detected; ping loop started after handshake (or after 3s timeout if no challenge).
4. Use the Jupiter AES key as the initial attempt. Document clearly that it is
   unverified on the RTR 310 and must be confirmed via btsnoop log.

## AES Key Status

**Jupiter key (initial attempt):** `7A A3 20 4D 16 1D B5 33 F4 EB 20 4F BC D7 3D D4`

**Verification method:** Enable HCI snoop log on Android, connect TVS Connect to
the RTR 310, capture bug report, extract btsnoop log, inspect the `0x9A 0xF1`
response packet in Wireshark. If the key is correct the bike will respond with
live telemetry; if incorrect the bike will ignore the response or disconnect.

## Alternatives Considered

- **No handshake — passive only:** Already tested. Bike does not stream telemetry
  without authentication. This approach is insufficient for Sprint 5+.
- **Hardcode the response without trying to decrypt:** Not viable — the challenge
  contains random bytes so the response changes every session.
- **Defer until key is confirmed:** Would block all telemetry work indefinitely.
  Implementing now with a clearly-marked hypothesis key is lower risk.

## Consequences

- **Positive:** If the key matches, the app immediately gains live telemetry access.
- **Positive:** `HandshakeManager` is isolated — easy to update the key without
  touching any other code.
- **Negative:** If the RTR 310 uses a different key, the handshake will fail
  silently (bike ignores the response). The ping still runs, keeping the
  connection alive, and the app remains functional as a passive logger.
- **Safety:** The only new WRITE operation is the handshake response and keep-alive
  ping, both documented in `docs/BLE-Protocol.md` and audited in
  `docs/security/BLE_WRITE_AUDIT.md`.

## Review Trigger

Update `HandshakeManager.JUPITER_AES_KEY` and move the key from Hypothesis to
Confirmed in `docs/KNOWN_FACTS.md` once verified via btsnoop log.
