- This is consistent with: `checksum = (C − sum(B0..B17)) % 256` for any constant C,
  because when one input byte decreases by 0x20, the sum decreases by 0x20,
  so the checksum must increase by 0x20. But the checksum also decreased by 0x20.

  - B1: sum(B0..B17) includes B10=0xCA. Checksum = 0xB2.

  consistent with `checksum = (C − sum(B0..B17)) mod 256`.

**CONFIRMED: For message 0x11, checksum = (0xC3 − sum(B0..B17)) mod 256**

> Note: 0xC3 may be a fixed constant for all messages, or it may vary per message ID.
> Cannot confirm universality from this data alone. The formula `(C − sum) mod 256`
> is equivalent to `(255 − sum mod 256) + (256 × k − 255 + C)` but simplest
> form: C = 0xC3 for the 0x11 message in this capture.

**Cross-check C=0xC3 against other message types:**

0x5A 0x10 (B18 = 0x01):
- sum = 5A+10+EA+EA+F6+24+DB+CA+EA+64+E5+6A+D8+CA+EA+EA+EA+EA
- = 90+16+234+234+246+36+219+202+234+100+229+106+216+202+234+234+234+234 = 3120 = 0xC30
- 0xC30 mod 256 = 0x30 = 48
- Expected if C=0xC3: (195 − 48) mod 256 = 147 = 0x93
- Actual B18 = 0x01 ← **MISMATCH**

So C is NOT 0xC3 universally. Either:
(a) Each message type has its own constant C, or  
(b) The checksum formula is per-message-type, or  
(c) The formula itself is different.

Let's derive C for 0x10:
- sum(B0..B17) = 3120, mod 256 = 48
- B18 = 0x01 = 1
- C = (B18 + sum mod 256) mod 256 = (1 + 48) mod 256 = 49 = 0x31

So for 0x10, C = 0x31. For 0x11, C = 0xC3. These differ — the constant is per-message-type.

The formula `checksum = (C − sum(B0..B17)) mod 256` does **not** hold for 0x5F

**Alternative hypothesis — per-message-type C that differs between C1 and C2:**

Derive C for C2 independently:
- sum(B0..B17) mod 256 = 0xE2 = 226
- B18 = 0x6B = 107
- C = (107 + 226) mod 256 = 333 mod 256 = 77 = 0x4D

C1 gives C=0x9D, C2 gives C=0x4D — not the same constant. So the formula is not
simply `(C − sum) mod 256` for 0x5F.

**Sum delta check:**
- sum(C2) − sum(C1) = 2530 − 2732 = −202 mod 256 = 54 (B1 is larger, so delta is negative; 
  as unsigned 8-bit: C2_sum_mod256 − C1_sum_mod256 = 226 − 172 = 54)
- checksum(C2) − checksum(C1) = 107 − 241 = −134 mod 256 = 122
- If simple additive: Δchecksum should be −Δsum = −54 mod 256 = 202. Actual = 122. **No match.**

**Conclusion for 0x5F:**
The checksum algorithm for message 0x5F is **UNRESOLVED**. Possibilities:
1. A rolling counter or nonce in the payload (B7 increments by 1 — this is a frame
   counter) feeds into the checksum separately from the byte sum.
2. The formula uses only a subset of bytes (not B0..B17).
3. The checksum is a different algorithm (CRC, polynomial, etc.) not matched by
   the tested set (CRC-8 with 5 polynomials was already attempted in Session 004).
4. There is a hidden state field that changes between frames.

- Checksum occupies **byte 18** (index 18, 0-based).
